Project Management Tool — Requirements & Feature Checklist

Reconciled against "Z Group — Project Portfolio Management Tool: Requirements Specification" · Generated 2026-06-22

☑ Met ◐ Partially met / deviation ☐ Not addressed

1. Overview & access (Spec §1–2)

  • Multi-user web app, ClickUp-styled, organized by business unit through a stage-gate process §1
  • Business units: ZFS, ZAM, ZGI, ZLA, Group Projects, ICT Initiatives — every project belongs to exactly one §1
  • Multiple users can log in and enter/update data §2
  • Read-only "viewer" role for stakeholders to view dashboards/reports §2
  • Authentication: spec asked for an established, audited backend-as-a-service (Supabase/Firebase-style). Built instead as custom PHP sessions — bcrypt-hashed passwords, prepared statements throughout, role checks on every endpoint, so it is functionally secure, but it is not the suggested managed provider. §2, §5

2. Information architecture & project fields (Spec §3–4.3)

  • Workspace → Portfolio Summary + per-Business-Unit → Project → Overview / Update & Next Steps / Governance §3
  • Business units shown as top-level spaces in the left sidebar with project counts, expandable §4.1
  • Selecting a business unit opens its dashboard §4.1
  • Add / edit / delete a project, with delete confirmation; every project requires a business unit §4.2
  • All data-model fields present: name, business unit, stage gate, status, owner, priority, two independent dates, progress, current update, next steps, governance §4.3
  • Owner field: spec defined it as free text ("person or dept responsible"). At the stakeholder's later request this evolved into a real user reference, so productivity could be tracked reliably — any role can be an owner, matching the spirit of the original field. §4.3

3. Stage gates, status & governance (Spec §4.4, 4.6, 4.7)

  • Six stage gates in order: Initiation → Planning → Execution/Development → QA → UAT → Project Closure §4.4
  • Update & Next Steps tab, free text, saved per project, with history retained §4.5
  • Status: On Track / At Risk / Behind Schedule / Complete, with Overdue auto-derived (red) when the completion date has passed and the project isn't Complete §4.6
  • Stage gate due date also flags separately when passed §4.6
  • Governance checklist — the exact 7 deliverables from the spec table, each with all 4 states (Pending / In progress / Signed off / N/A) and a roll-up % §4.7

4. Views, filtering & summaries (Spec §4.8–4.10)

  • List view grouped by stage gate, columns for status/owner/governance %/dates, collapsible groups §4.8
  • Kanban Board view, one column per stage gate §4.8
  • Search by project name §4.9
  • Filter by status (including Overdue / Behind Schedule), business unit, and assignee §4.9
  • Portfolio Summary: totals, status counts, average progress, per-business-unit breakdown cards, and a cross-portfolio "Needs Attention" list of overdue/behind/at-risk projects §4.10
  • Per-business-unit summary with the same statistics plus a stage-gate distribution §4.10
  • Full project list viewable both per-business-unit and as a whole portfolio §8 (closing note)

5. Reporting, import & sharing (Spec §4.11–4.13)

  • Status report for the current selection / date range §4.11
  • Report copyable, downloadable (text and CSV — Excel and PDF added beyond spec), and printable/PDF §4.11
  • Gantt chart downloadable for sharing with stakeholders §4.11
  • History of updates retained over time §4.11
  • Excel import, one row per project, flexible case-insensitive column-header mapping §4.12
  • Import: most fields blank when absent as required (owner, dates, progress, update text); stage/status/priority specifically fall back to a sensible default (e.g. "Initiation"/"On Track"/"Normal") rather than blank, since those three are required enums the rest of the app depends on §4.12
  • Multiple users contribute updates; shareable read-only link for stakeholder dashboards/reports §4.13

6. Non-functional requirements (Spec §5)

  • Multi-user, server-side persistence (MySQL) — no data loss on refresh §5
  • Security: bcrypt password hashing, RBAC on every endpoint, prepared statements everywhere (no SQL injection surface) — but not the suggested managed auth provider; "encrypted in transit" depends on TLS being configured at the hosting/deployment layer, not yet verified for production §5
  • Server-side validation on every write endpoint (the real gatekeeper, per spec wording); client-side validation on required fields §5
  • Privacy & compliance: no consent flow or documented data-retention policy implemented yet §5
  • Reliability under concurrent edits: handled via database transactions on multi-step writes; no explicit conflict-detection UI (e.g. "this project changed since you opened it") §5
  • Responsive: works on desktop and mobile (off-canvas nav, stacked drawer). Keyboard/contrast accessibility not formally audited §5
Flagged for your attention: privacy/compliance (consent + retention policy) and a formal accessibility pass are the two items from the non-functional requirements that haven't been addressed — worth a decision on whether they're in scope before go-live.

7. Stretch items explicitly listed in the spec (Spec §7)

  • Calendar and Gantt views as tabs
  • Automated notifications / email alerts — daily overdue alerts, weekly digest, and in-app notifications (assignment/accept/reject/@mentions) added beyond what was asked
  • Time tracking, budgets/financials, resource allocation — all three built, plus automatic red-flagging when actual cost exceeds budget
  • Gantt chart for each individual project

8. Beyond the spec — additional features added

Productivity & visibility

  • Activity feed — human-readable log of who did what, when
  • Global Cmd/Ctrl+K command palette — instant project search
  • Filters popover — owner, assignee, status, business unit, tag, stakeholder, all combinable
  • Tags/labels on projects
  • Threaded comments with @mentions — mentioned users get an in-app notification
  • File attachments on governance checklist items
  • Auto-generated Executive Summary (rule-based narrative, no external AI cost)

Owner / Assignee / Stakeholder model

  • Owner ("Assigned To") — the developer doing the work, any role, tracked for productivity
  • Assignee — the editor/admin who allocated the project, tracked for allocation performance (role-restricted visibility: editors see only their own, admins see everyone)
  • Stakeholder — a new entity for people with expectations of / contributions to a project, separate from owner and assignee
  • Stakeholders tab (first tab in the project drawer) with notes and requirements document upload (pdf/doc/docx/txt)
  • Multi-assignee allocation % with a Resources heatmap and over-allocation warnings
  • Cross-project dependencies with cycle detection

In-app notifications & allocation workflow

  • Notification bell with unread-count badge
  • New/reassigned owner notified automatically; can accept ("Start Working") or reject with a reason
  • Rejection notifies the assignee(s), who can reassign — full cycle repeats, history retained
  • @mention in a comment notifies the mentioned person
  • Clicking any notification opens the relevant project directly

Reporting & analytics

  • Owner (Developer) Productivity report — completion rate, average days to close, active workload vs. team-average "sweet spot," over/under-capacity flagging
  • Assignee (Allocator) Performance report — role-restricted as above
  • Per-project and portfolio-wide over-budget figures shown in red automatically

UI / UX

  • Unified List/Board view, loading skeletons, Gantt auto-scroll-to-today
  • Custom confirm/share-link modals replacing native browser dialogs, with copy-to-clipboard
  • Dashboard de-duplication — removed stat cards that repeated the status rings below them
